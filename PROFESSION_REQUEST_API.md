# Заявка на новую профессию

Профессии, которых нет в справочнике `GET /api/profession-categories/`,
пользователь запрашивает через заявку. Заявка подаётся из двух мест и попадает
в одну очередь модерации (админка → «Заявки на профессии»).

## 1. Из анкеты — `POST /api/apply/`

Вместе с `customProfession` принимается необязательное
`customProfessionDescription` (строка до 500 символов). Оно сохраняется в
анкете, показывается модератору рядом с названием (и в админке, и в Telegram-карточке
заявки) и автоматически создаёт заявку на профессию с источником «анкета».

```json
{
  "customProfession": "Кинолог",
  "customProfessionDescription": "Кинолог — это специалист, который занимается дрессировкой собак"
}
```

`customProfession` без описания (старые сборки) по-прежнему валиден. Описание без
`customProfession` игнорируется.

## 2. Из профиля — `POST /api/profession-requests/`

Авторизованный запрос (Bearer). Доступен любой роли, в том числе клиентам.

```json
{
  "name": "Кинолог",
  "description": "Кинолог — это специалист, который занимается дрессировкой собак"
}
```

Оба поля обязательны и непустые после `trim`; `name` — до 100 символов,
`description` — до 500. Лишние пробелы внутри названия схлопываются.

Успех — `201 Created`:

```json
{
  "id": 41,
  "name": "Кинолог",
  "description": "…",
  "status": "pending",
  "reason": "",
  "source": "profile",
  "createdAt": "2026-09-16T12:38:00+06:00",
  "professionCategory": null
}
```

`status`: `pending` | `approved` | `rejected`. `reason` — причина отказа,
`professionCategory` — id категории после одобрения.

Ошибки — в общем формате `code` + `message` (см. `API_ERROR_CODES.md`),
`message` можно показывать пользователю как есть:

| Случай | HTTP | `code` |
|---|---|---|
| пустое или слишком длинное `name` / `description` | 400 | `VALIDATION_ERROR` + `errors` по полям |
| нет токена | 401 | `NOT_AUTHENTICATED` |
| профессия уже есть в справочнике (без учёта регистра, включая подкатегории) | 409 | `CONFLICT`, «Профессия „Кинолог“ уже есть в списке — выберите её» (+ `professionCategory` с id) |
| у пользователя уже есть заявка `pending` с таким названием | 409 | `CONFLICT`, «Заявка на эту профессию уже на проверке» |
| больше 10 заявок в час (`PROFESSION_REQUESTS_THROTTLE_RATE`) | 429 | `THROTTLED` |

Отклонённую заявку можно подать заново.

## 3. Свои заявки — `GET /api/profession-requests/`

Список заявок текущего пользователя (оба источника), новые первыми, в том же
формате, что и ответ на создание. Нужен для экрана «на проверке / отклонено».

## 4. Модерация

Очередь — админка, раздел «Заявки на профессии»: название, описание, кто подал,
источник (анкета / профиль), дата. Решение принимается сменой статуса в карточке
или массовым действием «Одобрить выбранные».

Одобрение:

- категория берётся из поля «Категория после одобрения», если модератор её выбрал
  (например, хочет привязать к существующей); иначе берётся уже существующая с
  таким же именем; иначе создаётся новая верхнеуровневая категория с названием
  заявки. Она сразу видна в `GET /api/profession-categories/`;
- заявка из анкеты: категория проставляется в анкету как `profession`. Если
  анкета ещё на рассмотрении — профессия попадёт в профиль при её одобрении; если
  анкета уже принята — профессия сразу ставится специалисту;
- заявка из профиля: специалисту профессия ставится в профиль сразу; клиенту
  (ещё не специалисту) профиль не трогаем — он выберет её в анкете.

Отклонение — `status: rejected`, причина хранится в `reason`.

В обоих случаях заявителю уходит push и запись в `GET /api/notifications/`:
тип `profession_request_approved` (в `payload` — `professionRequestId`,
`professionCategoryId`) или `profession_request_rejected` (`reason`).
Источник — `profichat`.
