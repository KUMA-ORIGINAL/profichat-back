# Справочник ErkinAI: сотрудники при регистрации и синхронизация организаций

Две входящие ветки интеграции с ErkinAI (NewCRM). Обе ходят на его эндпоинты
`/api/integration/profichat/*` и авторизуются общим секретом
`MEDCRM_SSO_INTEGRATION_SECRET` в заголовке `X-Integration-Secret` — тем же,
которым ErkinAI проверяет у нас одноразовые SSO-токены.

**Секрет живёт только на бэкенде.** В приложение он не уезжает: и поиск
сотрудника, и синхронизация — межсерверные вызовы.

| Что | Наш код | Ручка ErkinAI |
|---|---|---|
| Есть ли у регистрирующегося карточка сотрудника | `integrations/erkinai/staff.py` | `POST /api/integration/profichat/staff-lookup/` |
| Зеркало справочника организаций | `integrations/erkinai/organization_sync.py` | `GET /api/integration/profichat/organizations/` |

## Настройка

```
MAMADOC_API_URL=https://newcrm.pediatr.kg      # тест: https://test.crm.operator.kg
MEDCRM_SSO_INTEGRATION_SECRET=<общий секрет>
MAMADOC_TIMEOUT=10
```

Отдельных переменных для этих двух веток нет — специально: адрес CRM и секрет
интеграции должны быть одни на всё приложение, иначе однажды разъедутся.

Со стороны ErkinAI интеграцию включают `PROFICHAT_LOOKUP_ENABLED=true` и тем же
секретом. Пока не включили — обе ручки отвечают `404`, и мы это трактуем как
«интеграции здесь нет»: регистрация идёт как обычно, синхронизация молча
пропускает запуск.

## 1. «Вы врач из ErkinAI?» при регистрации

`POST /api/auth/sms/verify/` (существующий вход по SMS) теперь возвращает
дополнительное поле:

```json
{
  "refresh": "...",
  "access": "...",
  "streamToken": "...",
  "erkinaiSpecialistOffer": [
    {
      "id": 42,
      "fullName": "Осмонова Айгуль Кубанычбековна",
      "phone": "+996700111222",
      "email": "doc@example.com",
      "photoUrl": "https://newcrm.pediatr.kg/media/...jpg",
      "specialties": ["Педиатр"],
      "primarySpecialty": "Педиатр",
      "experienceYears": 7,
      "bio": "...",
      "education": "КГМА, 2012",
      "languages": ["ru", "kg"],
      "consultationType": "in_person",
      "gender": "female",
      "hasCrmAccount": true,
      "organization": {"id": 1, "slug": "pediatr", "name": "Педиатр"},
      "branch": {"id": 3, "slug": "central", "name": "Центральный"}
    }
  ]
}
```

Пустой список — предлагать нечего, обычная регистрация. Уже существующему
специалисту предложение не приходит.

Поле **никогда** не роняет вход: недоступный, не настроенный или выключенный
ErkinAI даёт пустой список, а не ошибку.

### Принять предложение

```
POST /api/auth/erkinai/become-specialist/
Authorization: Bearer <access>

{"employeeId": 42}
```

Ответ `200`: `{"role": "specialist", "organizationId": 1, "employeeId": 42}`.

Что происходит: роль меняется на `specialist`, профиль дозаполняется данными
карточки (**только пустые поля** — то, что человек уже написал о себе, не
затирается), пользователь привязывается к организации.

| Код | Что случилось |
|---|---|
| `400` | не передан `employeeId` |
| `401` | нет токена |
| `404` | карточки с таким id по телефону **этого** пользователя нет |

Присланный `employeeId` сам по себе ничего не доказывает: бэкенд заново ищет
карточки по телефону авторизованного пользователя и принимает только ту, что
нашлась. Иначе любой клиент прислал бы чужой id и забрал чужой профиль вместе
с привязкой к чужой клинике.

### Почему это отдельное нажатие, а не автоматика

Номера операторы перевыпускают. Новый владелец номера уволившегося врача не
должен молча получить его имя, образование и клинику. Экран подтверждения с
кнопкой «нет, это не я» обязателен — см.
`docs/profichat-flutter-registration-guide.md` в репозитории ErkinAI.

## 2. Синхронизация организаций

```bash
python manage.py sync_erkinai_organizations          # инкрементально
python manage.py sync_erkinai_organizations --full   # полный проход
```

Крон: инкрементально хоть каждые 10 минут (запрос дешёвый — приходит только
изменившееся), полностью раз в сутки.

```cron
*/10 * * * * cd /app && python manage.py sync_erkinai_organizations
30 3 * * *   cd /app && python manage.py sync_erkinai_organizations --full
```

Полный нужен потому, что фид не сообщает о жёстком удалении: в ErkinAI
организации архивируют, а не удаляют, но филиал удалить могут — его адрес
подберёт только полный проход.

### Что синхронизация делает и чего не делает

* **Апсерт по `Organization.erkinai_id`**, а не по названию. Название у нас
  уникально и его правят руками — сопоставление по нему при первом же
  переименовании создало бы дубль.
* **Организации, заведённые в ProfiChat вручную, не трогаются вовсе.** У них
  `erkinai_id` пустой, и синхронизация их не видит.
* **Неактивная в ErkinAI гасится (`is_active=False`), а не удаляется.** На неё
  ссылаются профили специалистов; удаление порвало бы их. Расснятая с архива
  организация вернётся сама.
* **Филиалы становятся адресами** (`OrganizationAddress.erkinai_branch_id`).
  Пропавший из фида филиал забирает свой адрес; адреса, заведённые руками,
  остаются — синхронизация владеет только тем, что сама и привезла.
* **Тёзки не роняют запуск**: если название занято, организация из ErkinAI
  сохраняется как `«Название (ErkinAI #12)»` — видный след, дальше разбирает
  человек.

Отметка «докуда дошли» — `integrations.ErkinAISyncState` (одна строка на фид).
Двигается только после полного успешного обхода: упавший на середине запуск
повторится с прежней точки, а не сделает вид, что всё забрал.

Специалист, привязавшийся раньше, чем крон доехал до его клиники, не ждёт:
организация заводится сразу по данным карточки, а ближайшая синхронизация
найдёт её по `erkinai_id` и дополнит.
